Reliable MCP Tools in Production

Idempotency, timeouts, retries, rate limits, circuit breakers, and observability — with copy/paste patterns.

Why reliability is different for agent tools

Agent tools are invoked programmatically, often in parallel, sometimes repeatedly, and frequently under partial context. The tool layer is where you want to be strict: it should be safe to retry, predictable under load, and measurable.

  • Retries happen: the agent runtime may retry on network errors or timeouts.
  • Inputs drift: tools get called with imperfect data; validation is not optional.
  • Costs matter: APIs can be expensive; you need budget-aware guardrails.

1) Make writes idempotent

Any tool that creates, updates, or sends something (tickets, emails, payments, database rows) should accept an idempotencyKey and treat repeated calls as safe.

Minimal contract

{
  "idempotencyKey": "string",
  "request": { "...": "..." }
}

Behavior

  • If a request with the same idempotencyKey already succeeded, return the original success response.
  • If it is currently in-progress, return a deterministic “in progress” response or block until completion.
  • If the previous attempt failed, either allow retry (recommended) or return a stable failure.

Tip: keep an idempotency store keyed by (toolName, idempotencyKey) with a TTL.

2) Use explicit timeouts everywhere

A tool should fail quickly and clearly when downstream calls stall. Prefer multiple short timeouts (DNS/connect/read) over one long “overall” timeout.

  • Connect timeout: 2–5s
  • Read timeout: 15–30s (depends on API)
  • Overall timeout: 30–60s for most tools

If a workflow may take minutes, consider a pattern with start + poll tools instead of a single long call.

3) Retries: only for safe failures, with backoff + jitter

Retries are good for transient failures (HTTP 429/503, network resets), not for validation errors or 4xx.

Recommended policy

  • Max retries: 2–3
  • Backoff: exponential (e.g. 250ms, 1s, 4s)
  • Jitter: randomize delays to avoid thundering herds
  • Retry budget: cap total time spent retrying (e.g. 8–10s)

Retry decision table

FailureRetry?Notes
TimeoutYesOnly if the operation is idempotent or read-only.
429YesRespect Retry-After when provided.
502/503/504YesClassic transient gateway/API issues.
400/401/403/404NoFix input/auth; retries waste tokens and money.
Validation errorNoReturn a precise error and stop.

4) Rate limiting and concurrency control

Tools should protect downstream systems and prevent accidental fan-out. Implement both per-user rate limits and global concurrency caps.

  • Per-user limits: protect you from runaway agents and unexpected loops.
  • Global limits: keep the whole service stable under bursty traffic.
  • Concurrency caps per tool: expensive tools should have stricter limits than cheap ones.

If you can return a partial response (e.g., first 20 results) do it — it often avoids retries.

5) Circuit breakers and graceful degradation

If a dependency is failing, stop hammering it. A circuit breaker flips “open” after repeated failures and returns a fast error for a cooling period.

What to return when open

  • A stable error code (e.g. DEPENDENCY_UNAVAILABLE)
  • A short message describing what to do next (retry later, use alternative tool, reduce scope)
  • Optional: a fallback path (cached response, reduced fidelity)

6) Validation: reject early, return structured errors

Tool inputs should be strictly validated and errors should be actionable. Prefer machine-parseable errors so an agent can correct itself. 

{
  "error": {
    "code": "INVALID_ARGUMENT",
    "message": "startDate must be ISO-8601 (YYYY-MM-DD)",
    "field": "startDate"
  }
}

For enumerations (country codes, currencies, statuses), normalize and validate. If the agent sends close-but-not-valid values, return the allowed set.

7) Observability: logs, metrics, traces

Reliability is invisible until it breaks. Instrument tools so you can answer: what failed, why, for whom, and how often.

Minimum metrics

  • Requests: count by toolName, status, and error code
  • Latency: p50/p95/p99 by toolName
  • Retries: count + reasons
  • Rate-limited: count of 429 returned (internal or downstream)
  • Cost: per-call and per-user (if you pay per API call)

Structured logs

  • Always include: request id, tool name, user/tenant id (if available), idempotency key, duration, result status.
  • Never log secrets or raw PII; hash or redact.

8) Cost guards (token/API budget)

Agents can accidentally call tools in loops. Add budget checks: per-run, per-user/day, and per-tool.

  • Reject or downscope if the estimated cost exceeds the caller’s budget.
  • Expose a separate “estimate” tool for expensive actions (search, enrichment, extraction).
  • Cache aggressively for read-only endpoints.

Checklist

  • All write tools accept an idempotency key.
  • Timeouts set at every HTTP boundary.
  • Retries only for safe, transient failure modes.
  • Rate limits and concurrency caps in place.
  • Circuit breaker for flaky dependencies.
  • Strict input validation with structured errors.
  • Metrics + structured logs + traces (where possible).
  • Budget guards for expensive calls.
