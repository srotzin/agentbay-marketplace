How MCP tools phases work in AgentBay

A practical guide for adding and validating new tools without turning mcp-tools.js into a monolith.

Home Docs

Why phases exist

As AgentBay grows, the MCP tools catalog keeps expanding. If every tool definition lived in a single file, it would become hard to review, merge, and validate. Phases solve that by splitting the tool registry into small, thematic files that are loaded in order.

Design goal: Keep each phase easy to understand and safe to change, while still producing one complete exported tool list.

What a phase file looks like

Phase files typically live under src/mcp-tools-phases/ and export an array of tool definitions. Each tool definition follows a consistent schema (name, description, params, handler binding). 

// src/mcp-tools-phases/phase-XX-*.js

export default [
  {
    name: 'vertical__example__do_thing',
    description: 'Does a thing for the Example vertical.',
    inputSchema: {
      type: 'object',
      properties: { id: { type: 'string' } },
      required: ['id']
    },
    handler: async ({ id }, ctx) => {
      // ctx.services.exampleService.doThing(id)
      return { ok: true };
    }
  }
];

How phases get assembled

The top-level aggregator (commonly src/mcp-tools.js) imports the phase files and concatenates them into one tool list. This keeps ordering explicit and makes it trivial to add or remove phases. 

// src/mcp-tools.js

import phase20 from './mcp-tools-phases/phase-20-hitl.js';
import phase21 from './mcp-tools-phases/phase-21-new-verticals.js';

export const tools = [
  ...phase20,
  ...phase21,
];

The exact filenames and phase numbers vary by repo; the pattern is: add a new phase file, then wire it into the aggregator.

Recommended workflow to add a new tool

  1. Create or pick a phase file that matches your vertical/theme.
  2. Implement the service module under src/services/ if the tool needs new backend logic.
  3. Expose the tool in the phase file (bind the handler to the service).
  4. Wire the phase into src/mcp-tools.js if it’s a new phase file.
  5. Validate syntax and linting.
Check Command What it catches
Syntax (fast) node --check path/to/file.js Typos, missing brackets, invalid imports
Unit tests npm test Regression in behavior
Smoke run node src/mcp-server.js Runtime wiring issues (services not registered, missing env vars)

Common pitfalls

  • Tool name collisions: keep names namespaced (e.g., vertical__domain__action).
  • Overly large phase files: once a phase grows beyond a few dozen tools, split it.
  • Handlers doing too much: move business logic into a service module so the handler stays thin.

Next steps

If you’re adding a new vertical, start by cloning the structure of an existing vertical service (for example, a HITL-style module), then add a small phase file that exposes only a few high-value tools.
