How to Build an Agent Validation Suite

Tool-calling agents are hard to ship because the failure modes are subtle: partial tool success, schema drift, brittle prompts, or a single new tool changing the agent’s “plan”. This guide shows a practical validation pattern you can run in CI and before every deploy.

Goal

Catch regressions in agent behavior (tool selection, tool args, output quality, safety) using a repeatable suite of tasks + fixtures + scoring.

1) Define your “golden tasks”

A golden task is a real user job-to-be-done written as a compact scenario with an expected outcome. Keep it short enough to run frequently (minutes, not hours).

Good golden task

Scenario: Refund an order shipped to the wrong address
Inputs: order_id=..., user_email=...
Constraints: cannot refund if delivered > 30 days ago
Expected: create refund + email user + log audit event

Bad golden task

Scenario: Be helpful to customers
Expected: a good answer

Golden task template

id: refund_wrong_address_v1
persona: "Ops agent"
input: "Customer says they shipped to the wrong address. Order 913..."
fixtures:
  - "orders_api_stub"
  - "email_outbox_stub"
expectations:
  - tool_calls.include("orders.get_order")
  - tool_calls.include("payments.refund")
  - tool_calls.not_include("payments.charge")
  - output.contains("Refund initiated")
  - invariants.include("no PII in logs")
scoring:
  - rubric: helpfulness
  - rubric: policy_compliance
  - rubric: completeness

2) Add “synthetic users” (coverage for intent variance)

Golden tasks are stable; synthetic users are variants. For each golden task, generate 10–50 variations that change wording, missing fields, tone, and constraints.

Tip: keep the expected outcome stable while perturbing the input phrasing. This catches prompt brittleness.

3) Run against fixtures (deterministic tool behavior)

For tool-calling agents, determinism comes from using stubbed tool backends or recorded cassettes. Your goal is to validate the agent’s reasoning and tool selection, not the internet.

Fixture patterns

  • Stub services: In-memory fake implementations returning predictable data.
  • Recorded responses: Store tool IO transcripts and replay them.
  • Failure injection: Timeouts, partial success, 429s, schema drift.

4) Score what matters (not just “match output”)

Exact text matching is fragile. Instead, score:

  • Tool call correctness: called the right tools with valid args.
  • Safety invariants: no secrets/PII, no disallowed actions.
  • Task completion: user outcome achieved end-to-end.
  • Human-readability: concise, structured, no hallucinated confirmations.

Minimal scoring output format

{
  "task_id": "refund_wrong_address_v1",
  "passed": false,
  "tool_call_failures": ["payments.refund missing currency"],
  "policy_failures": [],
  "notes": "Agent asked for info already present in the order record"
}

5) Add regression gates (what fails the build)

The suite is only useful if it blocks shipping when it detects a real regression. Start with strict gates on safety, and gradual gates on quality.

Suggested gating policy

  • Hard fail: any safety invariant break (PII, secrets, unauthorized actions).
  • Hard fail: schema mismatch / invalid tool arguments above a threshold.
  • Soft fail: rubric score dips (helpfulness/completeness) → warn, track trend.
  • Trend alert: latency or tool-call count changes significantly.

6) Operationalize: nightly runs + a small “smoke suite”

Run a small smoke suite on every commit (5–20 tasks) and a larger suite nightly. Persist transcripts so you can diff tool calls and identify which new tool or prompt change caused drift.

Example: validating an MCP tool registry change

When you add tools (or reorganize tool phases), validate:

  • The registry loads and schemas are valid JSON.
  • New tools do not shadow old names.
  • Routing/dispatch paths still resolve correctly.
  • At least one golden task that should use the new tool actually uses it.

Practical checklist

  • Run syntax checks for the registry and service modules.
  • Run a smoke suite with fixtures (including timeouts and schema drift injection).
  • Diff tool transcripts vs baseline.
  • Ship only if hard gates pass.

Want a ready-to-run template? Use this structure: tasks/ (golden + variants), fixtures/ (tool stubs), runner/ (agent harness), and reports/ (JSON + HTML summaries).
