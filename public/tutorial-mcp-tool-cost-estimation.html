MCP Tool Cost Estimation: Tokens, Latency, and Rate Limits

If your agent uses tools (search, fetch, database, SaaS connectors), the real-world bill isn’t just LLM tokens. This guide shows a simple way to estimate cost and time, then reduce both without hurting quality.

Goal: predictable spend Goal: lower p95 latency Goal: fewer rate-limit incidents

1) Build a cost model (the 5 variables)

For a single agent run, estimate these:

LLM token cost

  • Input tokens: system + user + tool outputs you include
  • Output tokens: final answer + intermediate reasoning text (if any)
  • Price: per 1M tokens in and out (varies by model)

Tool/infra cost

  • Per-request fees (search APIs, paid connectors)
  • Compute time (serverless, containers)
  • Storage + egress (caching, object stores)

Basic equation

TotalCost ≈ (Tin/1e6)*Pin + (Tout/1e6)*Pout + Σ ToolFees + Infra
TotalTime ≈ CriticalPath(LLM calls + tool calls + retries + serialization)

Tip: Start with a spreadsheet that logs: tool name, calls per run, average payload size, cache hit rate, and p50/p95 latency. You can refine accuracy later.

2) Token budgeting for tool calls

The hidden token driver is usually tool output (long HTML pages, large JSON blobs, verbose logs). Reduce it intentionally.

Practical rules

  • Summarize at the boundary: Have the tool layer return only fields you need (or a short extracted summary).
  • Cap payloads: Use max-length parameters for web fetches; paginate API responses.
  • Deduplicate: Don’t re-inject the same tool output on later calls; store it in run state and reference it.

Quick back-of-the-envelope

ApproxTokens(text) ≈ chars / 4
Example: 40,000 chars of HTML ≈ ~10,000 tokens
If you include that in context 3 times, it’s ~30k input tokens.

Anti-pattern: “Fetch 5 pages in full HTML, paste all into the model, then ask for a 3-bullet summary.” Prefer: extract the 3 facts at fetch-time, then pass the facts.

3) Latency estimation (critical path)

Users feel the slowest chain of dependent calls, not the sum of everything. Estimate your critical path.

Steps

  1. Draw the run as a DAG: nodes are calls, edges are dependencies.
  2. Mark which calls can run in parallel (independent tool calls).
  3. Compute p95 time by summing p95s along the longest dependency chain.

What usually dominates

  • Network-bound tools (search, web reads, SaaS connectors)
  • Retries from transient errors
  • Large payload serialization (big JSON, images)
Example critical path:
LLM(plan) 1.2s
  -> search 0.9s
  -> fetch 1.5s
  -> fetch 1.4s (parallel)
  -> LLM(write) 1.4s
p95 ≈ 1.2 + max(0.9+1.5, 0.9+1.4) + 1.4 = 4.1s

4) Rate-limit planning and backoff

Rate limits hit hardest when you parallelize aggressively. Plan for them explicitly.

Strategies

  • Token bucket per provider: cap concurrent calls and calls per minute.
  • Exponential backoff with jitter on 429/503.
  • Progressive degradation: if rate-limited, fall back to fewer sources or a cached snapshot.

Backoff pseudocode

delay = base
for attempt in 1..N:
  try call()
  if ok: break
  if status in {429, 503}:
    sleep(delay + rand(0, jitter))
    delay *= 2
  else:
    raise

5) Patterns that reduce cost and time

Batching

Combine independent lookups into one tool call if your backend supports it.

Caching

Cache tool results by a stable key (URL + headers + query). Add TTLs and invalidation rules.

Selective context

Pass only the “need-to-know” subset of prior tool outputs into later LLM calls.

Two-pass planning

First pass decides which sources are required; second pass fetches only those.
