Tutorial: Adding a New Service Module (and Wiring It into MCP Tool Phases)

This guide walks through the pattern used in this repo: define tools in src/services/<vertical>.js, expose them from a phase file (src/mcp-tools-phaseXX-*.js), then wire them into src/mcp-tools.js (tools array + handler dispatch).

What you will build

Outputs

  • A new service module in src/services/ exporting tool definitions and a handler.
  • A new MCP phase file in src/ that re-exports those tools for registration.
  • Updates to src/mcp-tools.js to register tools and dispatch calls to the right handler.

Repository conventions

  • Each tool has a JSON schema (inputSchema) and a short description.
  • Handlers receive (toolName, args) and return a plain object.
  • Tool registration happens by concatenating arrays from phase files.
Tip: Keep the tool name stable. If you rename a tool, you may break downstream prompts that reference it.

Step 1 — Create a service module

Pick a vertical and create src/services/my-vertical.js. A typical module exports:

  • myVerticalTools — an array of tool definitions
  • handleMyVerticalTool — the dispatcher for those tools
// src/services/my-vertical.js
export const myVerticalTools = [
  {
    name: "my_tool_name",
    description: "One-sentence description of what the tool does.",
    inputSchema: {
      type: "object",
      properties: {
        example: { type: "string", description: "Example input" }
      },
      required: ["example"],
      additionalProperties: false
    }
  }
]

export async function handleMyVerticalTool(toolName, args) {
  switch (toolName) {
    case "my_tool_name": {
      // Do work here (validate args, call libs, etc.)
      return { ok: true, echo: args.example }
    }
    default:
      return null
  }
}
Common bug: Forgetting additionalProperties: false can make inputs ambiguous and harder to validate.

Step 2 — Add a new MCP tool phase file

Create a new phase file that exports an array. This keeps src/mcp-tools.js from becoming a single huge tools list.

// src/mcp-tools-phaseNN-my-vertical.js
import { myVerticalTools } from "./services/my-vertical.js"

export const tools = [
  ...myVerticalTools,
]
Tip: Group related verticals in a single phase file when they are small; split into multiple phase files when the tools list grows.

Step 3 — Wire into src/mcp-tools.js

There are two changes: register the tools and route tool calls to your handler.

3A) Import the phase tools

import { tools as phaseNNTools } from "./mcp-tools-phaseNN-my-vertical.js"

3B) Add to the tools array

const toolsArray = [
  // ...existing phases...
  ...phaseNNTools,
]

3C) Add handler dispatch

Most implementations do a chain of handler calls until one returns a non-null response.

import { handleMyVerticalTool } from "./services/my-vertical.js"

// ...
const result =
  (await handleMyVerticalTool(toolName, args)) ??
  (await handleOtherTool(toolName, args))

if (result == null) throw new Error(`Unknown tool: ${toolName}`)
return result
Common bug: Exporting tools but forgetting dispatch means the tool registers fine, but will fail at runtime when called.

Step 4 — Sanity checks

  • Run a syntax check: node --check src/mcp-tools.js
  • Optionally, run your unit tests (if present).
Tip: If you add many tools at once, you can quickly validate the registration list by grepping for the tool name in src/mcp-tools.js.

FAQ

How do I choose a good tool boundary?

Prefer tools that do one thing and are easy to describe in a prompt. If a tool needs multiple steps, build two tools (e.g., plan_* and execute_*).

What should the handler return?

Return a JSON-serializable object. Keep it stable over time (use versioned fields if you need to evolve it).

Do I need a new phase file every time?

No. If the vertical is closely related to an existing phase, add it there. Create a new phase when the phase would otherwise become too broad.
