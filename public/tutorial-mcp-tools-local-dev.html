Local MCP Tools Development: Add a New Service Module End-to-End

A step-by-step workflow for adding a new vertical module under src/services/, wiring it into the MCP router, and validating locally before pushing.

What you will build

You will add a new service module (a vertical) with several MCP tools, then wire it into the router so the tools appear in tools/list.

  • Create a new module file in src/services/
  • Add it to a new src/mcp-tools-phaseXX.js aggregation file
  • Register the tools in src/mcp-tools.js (imports, tools array, dispatch chain)
  • Run a fast syntax check: node --check src/mcp-tools.js

1) Pick a vertical and design tool boundaries

Good vertical modules share a pattern: a small set of CRUD-like tools plus 1–2 "workflow" tools that do something opinionated.

Example tool set

// mcp name suggestions
vertical_list_resources
vertical_get_resource
vertical_create_resource
vertical_update_resource
vertical_delete_resource
vertical_run_workflow

2) Add the service module

Create a new file in src/services/. Follow existing modules for naming, JSON schema shapes, and error handling.

Minimal skeleton

// src/services/my-vertical-tools.js
export const myVerticalTools = [
  {
    name: "my_vertical_ping",
    description: "Sanity check tool for the vertical",
    inputSchema: { type: "object", properties: {}, additionalProperties: false },
    async handler() {
      return { ok: true };
    }
  }
];

3) Wire into a new phase file

The project groups tools into phase files. Create a new phase file that imports your module and exports a combined array.

// src/mcp-tools-phaseXX.js
import { myVerticalTools } from "./services/my-vertical-tools.js";

export const toolsPhaseXX = [
  ...myVerticalTools,
];

The phase filename can be any unused number. Keeping phases small helps reduce merge conflicts.

4) Register tools + dispatch in src/mcp-tools.js

Most bugs happen here: forgetting the import, forgetting to add tools to the exported list, or missing the handler case.

Checklist

  • Import the new phase file export
  • Append the phase to the tools array
  • Add dispatch cases so tool.name routes to tool.handler

Dispatch pattern

// pseudo-structure
if (tool.name === "my_vertical_ping") {
  return await tool.handler(args);
}

5) Local verification

Before committing, do a cheap syntax pass and optionally run a quick node script that imports the new phase and prints tool names.

# fast syntax check
node --check src/mcp-tools.js

# optional: ensure no duplicate tool names
node -e 'import("./src/mcp-tools.js").then(m=>{const names=m.tools.map(t=>t.name); console.log(names.length, new Set(names).size);})'

6) Safe git workflow (avoids push rejection)

If other automation is landing commits, pushing without rebasing can fail.

git add -A
git commit -m "Add new vertical"
git pull origin master --rebase
git push origin master

If the rebase hits conflicts: resolve, git add, then git rebase --continue.

Common gotchas

  • Duplicate tool names (two modules exporting the same name)
  • Input schemas allowing unexpected properties (set additionalProperties: false where appropriate)
  • Handler returning non-JSON-safe values (return plain objects/arrays/strings)
  • Forgetting to add the module into the phase file and the phase into mcp-tools.js

If you want a template vertical, search existing modules under src/services/ and copy the smallest one as a starting point.
