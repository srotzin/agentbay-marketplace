Agent Observability: tracing, spans, and structured logs

A practical guide for AgentBay-style service modules and MCP tool handlers.

Goal: make every tool invocation debuggable without leaking secrets. This tutorial shows a minimal pattern for tracing, span boundaries, structured logging, and redaction.

Why observability matters for agents

Fast debugging

When a tool returns the wrong data, you need a timeline: inputs, downstream calls, retries, and outputs.

Safety + compliance

You want to log enough to reproduce issues while redacting tokens, API keys, emails, or personal data.

A minimal tracing model

  • trace_id: one per user request / agent turn
  • span_id: one per tool call or meaningful internal step
  • parent_span_id: links tool spans to the request span
  • events: structured log records, not unstructured strings

Pattern: add a request context

Start by attaching context to every invocation.

// pseudo-code
function makeContext({ requestId, userId }) {
  return {
    trace_id: requestId,
    user_id: userId,
    started_at: new Date().toISOString(),
  };
}

Pattern: structured logs

Prefer JSON objects with consistent keys:

// pseudo-code
log.info({
  trace_id,
  span_id,
  tool: "search_web",
  stage: "start",
  input: redact(input),
});

Redaction rules

  • Always redact: authorization, api_key, token, cookie
  • Partially redact emails/phones unless needed for matching
  • Cap large fields (e.g. first 2k chars of HTML responses)
// pseudo-code
function redact(obj) {
  const SENSITIVE = [/token/i, /api[_-]?key/i, /authorization/i, /cookie/i];
  return deepMap(obj, (k, v) => {
    if (SENSITIVE.some(r => r.test(String(k)))) return "[REDACTED]";
    if (typeof v === "string" && v.length > 2000) return v.slice(0, 2000) + "…";
    return v;
  });
}

Span boundaries for service modules

In AgentBay-style src/services/* modules, add spans for each external dependency:

// pseudo-code
async function handler(input, ctx) {
  const span = startSpan({ name: "service.weather.forecast", trace_id: ctx.trace_id });
  try {
    log.info({ ...span, stage: "start", input: redact(input) });

    const httpSpan = startSpan({ name: "http.get", parent_span_id: span.span_id, trace_id: ctx.trace_id });
    const res = await fetch(url);
    log.info({ ...httpSpan, stage: "end", status: res.status });

    const out = await res.json();
    log.info({ ...span, stage: "end" });
    return out;
  } catch (err) {
    log.error({ ...span, stage: "error", error: String(err) });
    throw err;
  } finally {
    endSpan(span);
  }
}

Attach trace IDs to user-visible errors

When a tool fails, return a short error with a trace ID so you can find the logs quickly.

{
  "ok": false,
  "error": "Upstream timeout",
  "trace_id": "req_01H...",
  "hint": "Retry in 30s or lower max_results"
}

Checklist

  • Every tool call logs: start and end events with duration
  • Inputs/outputs pass through redact()
  • Errors include trace_id and a short actionable hint
  • Large payloads are truncated before logging
  • No secrets are logged (verify with unit tests)
