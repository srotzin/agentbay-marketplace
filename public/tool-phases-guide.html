How HiveAgent Tool Phases Work (and How to Add Your Own)

HiveAgentIQ organizes MCP tools into “phases” so the tool catalog can grow without becoming a single, unmaintainable file. This guide explains the structure and provides a safe checklist for adding a new phase.

What is a tool phase?

A “phase” is a small, versioned module that exports a set of MCP tool definitions (name, description, input schema, and handler). Instead of putting hundreds of tools in one file, HiveAgentIQ breaks the catalog into sequential phase files (for example mcp-tools-phase17.js, mcp-tools-phase25.js).

This is a code-organization pattern: phases do not necessarily represent chronological releases in production; they represent manageable batches of tools with consistent wiring.

How files are organized

In the repository, phase files typically live alongside the rest of the MCP tool wiring, and each phase file exports a function (or object) in the same style as prior phases.

Typical shape of a phase module

// mcp-tools-phaseNN.js

export function registerPhaseNN({ registerTool }) {
  registerTool({
    name: 'some_tool',
    description: '…',
    inputSchema: { /* JSON schema */ },
    handler: async (args, ctx) => { /* … */ }
  })
}

Exact names vary. The key is consistency with the existing phase pattern in your codebase.

How dispatch works in mcp-tools.js

mcp-tools.js is the router and registry. It imports each phase module, registers tools for listing, and ensures incoming tool calls are dispatched to the correct handler.

When you add a new phase:

  • You add a new import for the phase file.
  • You register the phase in the tool registration pipeline so its tools appear in tools/list.
  • You ensure the dispatch logic recognizes the new tools (often automatic if the registry is shared).

If the system uses explicit switch cases for phases, update them too. If it uses a shared map, only the import + registration are needed.

Checklist: add a new phase safely

  1. Pick a phase number that doesn’t exist yet.
  2. Create the phase file and copy the structure from the most recent phase.
  3. Keep tools cohesive: a phase should have a clear theme (example: “Security hardening” or “New verticals”).
  4. Update mcp-tools.js to import and register the phase.
  5. Run a syntax check on new/changed files:
node --check path/to/new-file.js
  1. Run tool listing locally (or in your test environment) and confirm your new tools appear.
  2. Sanity test at least one handler end-to-end.
Tip: If you are adding API-backed tools, implement safe JSON parsing and include error messages that are helpful to the agent (not just stack traces).

Common errors and how to avoid them

Tools don’t appear in tools/list

  • Phase file exists but was not imported in mcp-tools.js.
  • The registration function wasn’t invoked.
  • The exported symbol name doesn’t match what mcp-tools.js expects.

Runtime error on first tool call

  • Handler throws on undefined optional fields; add defaults.
  • External API response is not JSON; use guarded parsing.
  • Missing environment variables; validate at startup and return actionable errors.

Duplicate tool names

  • Search for existing tool names before adding a new one; collisions can break dispatch.
