Incident Status MCP Tools: declare → update → resolve

This guide shows a repeatable workflow for production incident communication using HiveAgent MCP tools. You will declare an incident, post structured updates, resolve it, and generate a status-page-ready summary.

Why this pattern works

  • Speed: one tool to declare, one to post an update, one to resolve.
  • Consistency: the tools enforce a minimal incident schema (impact, severity, timestamps, updates).
  • Multi-channel ready: the same update objects can be used for a status page, Slack, email, or Zendesk macros.

Tools used (incident-status vertical)

  • incident_status_declare — open an incident and set impact + severity
  • incident_status_update — add timeline updates and mitigation notes
  • incident_status_resolve — close incident with RCA summary
  • incident_status_summary — produce a status-page-style narrative summary

Pre-flight checklist

  • Know the affected services/components (API, dashboard, payments, etc.).
  • Pick a severity scale and stick to it (SEV-1..SEV-4 or similar).
  • Decide your update cadence (e.g., every 15 minutes for SEV-1).

Minimal incident schema

These are the fields you should always include for reliable downstream formatting.

{
  "title": "API latency and elevated 5xx",
  "severity": "SEV-1",
  "impact": {
    "user_impact": "Checkout timeouts for some users",
    "regions": ["eu-west"],
    "components": ["api", "checkout"]
  },
  "started_at": "2026-04-09T16:20:00Z"
}
Tip: keep the title short and user-facing. Avoid internal hostnames or ticket IDs.

Step-by-step workflow

1) Declare the incident

// Declare an incident
{
  "tool": "incident_status_declare",
  "args": {
    "title": "API latency and elevated 5xx",
    "severity": "SEV-1",
    "impact": {
      "user_impact": "Checkout timeouts for some users",
      "regions": ["eu-west"],
      "components": ["api", "checkout"]
    },
    "started_at": "2026-04-09T16:20:00Z"
  }
}

// Returns
{
  "incident_id": "inc_01H...",
  "status": "open"
}

2) Post a customer-facing update

{
  "tool": "incident_status_update",
  "args": {
    "incident_id": "inc_01H...",
    "message": "We are investigating elevated API latency and 5xx errors affecting checkout.",
    "status": "investigating",
    "timestamp": "2026-04-09T16:28:00Z"
  }
}

3) Add mitigation updates

{
  "tool": "incident_status_update",
  "args": {
    "incident_id": "inc_01H...",
    "message": "We have rolled back a configuration change and are monitoring recovery.",
    "status": "mitigating",
    "timestamp": "2026-04-09T16:42:00Z"
  }
}

4) Resolve with a short RCA summary

{
  "tool": "incident_status_resolve",
  "args": {
    "incident_id": "inc_01H...",
    "resolved_at": "2026-04-09T17:05:00Z",
    "resolution": {
      "summary": "A misconfigured rate limiter caused elevated 5xx errors. We rolled back to a safe configuration.",
      "followups": [
        "Add staged rollout + canary checks to rate limiter changes",
        "Add alert for rate limiter saturation"
      ]
    }
  }
}

5) Generate a status-page narrative summary

{
  "tool": "incident_status_summary",
  "args": {
    "incident_id": "inc_01H...",
    "format": "status_page"
  }
}

// Returns
{
  "summary": "Between 16:20 and 17:05 UTC, some users experienced checkout timeouts due to elevated API errors..."
}
Operational rule of thumb: if you can’t say what changed since the last update, still post an update that says that (it reduces support load).

Recommended templates

Investigating

We are investigating reports of [symptom].
Impact: [who is affected, what they see].
Next update: [time].

Identified / Mitigating

We identified [cause class] and are applying mitigation.
Current status: [what changed since last update].
ETA: [if known] or Next update: [time].

Resolved

The incident is resolved.
Root cause: [short, user-safe explanation].
Prevention: [1–3 follow-ups].

Note: avoid sharing sensitive internal details in customer updates. Keep technical details for internal postmortems.
