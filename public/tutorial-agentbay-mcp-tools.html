Build an MCP Tool in AgentBay: Service Modules + Phases

This guide shows the typical AgentBay pattern for adding a new MCP tool: implement a service module, expose it in a phase file, and wire it into the main dispatcher.

When to use

Add a new capability (a “tool”) that should be available to agents via MCP, and keep the implementation isolated by vertical or domain.

What you’ll build

A new service module in src/services/, a new phase file that lists the tool(s), and dispatcher wiring in src/mcp-tools.js.

Expected outcome

Your tool appears in MCP tools/list, and calls route to the right handler implementation.

Architecture at a glance

AgentBay typically separates concerns into three layers:

  • Service module (vertical implementation): domain logic + external API calls.
  • MCP tools phase file: tool definitions (name, description, input schema) grouped for maintainability.
  • Main MCP router (src/mcp-tools.js): combines tool arrays and dispatches tool calls to service handlers.

Step 1 — Create a service module

  1. Create a new file under src/services/ named for the vertical (example: src/services/security-posture.js).
  2. Export a handler function that accepts (args, ctx) (or whatever the project’s convention is) and returns a JSON-serializable result.
  3. Keep I/O boundaries explicit: validate inputs, call the external dependency, normalize the output.

Example skeleton

// src/services/security-posture.js

export async function checkSecurityPosture(args, ctx) {
  const { target } = args;
  if (!target) {
    return { ok: false, error: "Missing required field: target" };
  }

  // 1) Call dependency (API / internal library)
  // 2) Normalize response
  // 3) Return a stable shape for downstream agents
  return {
    ok: true,
    target,
    summary: "...",
    findings: []
  };
}

Step 2 — Define the tool in a phase file

  1. Add a new phase file, e.g. src/mcp-tools-phase64.js.
  2. Export an array (or a function returning an array) of tool specs.
  3. Each tool spec should include a name, description, and JSON Schema for inputs.

Example tool definition

// src/mcp-tools-phase64.js

export const toolsPhase64 = [
  {
    name: "security_posture_check",
    description: "Assess a target's security posture from public signals.",
    inputSchema: {
      type: "object",
      additionalProperties: false,
      properties: {
        target: { type: "string", description: "Domain or identifier" }
      },
      required: ["target"]
    }
  }
];

Step 3 — Wire the phase file into mcp-tools.js

  1. Import your new phase export and add it to the combined toolsArray (or equivalent aggregator).
  2. Import your new service handler(s).
  3. Extend the dispatch chain so calls to security_posture_check route to checkSecurityPosture.

Dispatcher pattern (illustrative)

// src/mcp-tools.js

import { toolsPhase64 } from "./mcp-tools-phase64.js";
import { checkSecurityPosture } from "./services/security-posture.js";

const toolsArray = [
  // ...previous phases...
  ...toolsPhase64
];

export async function handleToolCall(name, args, ctx) {
  if (name === "security_posture_check") {
    return checkSecurityPosture(args, ctx);
  }
  // ...other handlers...
  throw new Error(`Unknown tool: ${name}`);
}

Step 4 — Sanity-check locally

  • Run a syntax check on the dispatcher file: node --check src/mcp-tools.js
  • Optionally run whatever unit tests or smoke tests exist in the repository.

Tip: if the repo uses ESM, ensure your new module exports align with the existing import style.

Common pitfalls

  • Name mismatches: tool name in phase file must match dispatch string exactly.
  • Schema drift: document required fields and keep schemas strict (additionalProperties: false where possible).
  • Non-deterministic outputs: normalize external responses so agents get stable shapes.
  • Silent failures: return actionable error fields rather than empty objects.

Next steps

Once you have the pattern working, consider:

  • Adding basic validation helpers shared across services.
  • Creating “vertical bundles” that group related tools for easier discovery.
  • Writing a short example prompt for agents showing how to call the tool.
