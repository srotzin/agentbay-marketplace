How HiveAgentIQ MCP Tools Work (and How to Add Your Own)

A practical guide for adding a new service module and wiring it into the MCP tool registry.

Use case: You have a new vertical or capability (e.g., “telecom plan analysis”, “energy tariff comparison”, or “contract clause extraction”) and you want it to appear as an MCP tool that agents can call.

1) Mental model: “service modules” → “tools” → “handler”

AgentBay organizes MCP functionality into service modules under src/services/. Each module typically exports one or more tools, each with:

  • Metadata (name, description, input schema) used by tools/list
  • Handler code that runs when tools/call is invoked

A separate registry file (often an “mcp-tools phase” file) imports many modules and exports a single array. Finally, src/mcp-tools.js assembles arrays and dispatches each incoming call to the correct module handler.

2) Anatomy of a typical service module

Most modules follow a small set of conventions:

  • Export a tools array with one or more tool definitions
  • Export a handleToolCall function (or similarly named dispatcher)
  • Keep input validation close to the handler (or rely on shared validation helpers)
// src/services/example-vertical.js
export const tools = [
  {
    name: "example.vertical.lookup",
    description: "Look up something in a new vertical.",
    inputSchema: {
      type: "object",
      properties: {
        query: { type: "string" }
      },
      required: ["query"]
    }
  }
];

export async function handleToolCall(toolName, args, ctx) {
  if (toolName !== "example.vertical.lookup") return null;

  // ... do work here ...
  return {
    content: [{ type: "text", text: `Result for: ${args.query}` }]
  };
}

3) Wiring a module into the tool registry

Once your module exists, it has to be included in the aggregated tool arrays. Many AgentBay repos split the registry across “phase” files. When you add a new vertical, you typically:

  1. Create src/services/<your-module>.js
  2. Add a new phase file (or update an existing one) that imports your module and exports the combined tool array
  3. Update src/mcp-tools.js to import your phase array and add it to the global array
  4. Update the dispatch chain in src/mcp-tools.js so tools/call can reach your module’s handler

4) Dispatch chain: “list” and “call” must both work

A common mistake is to update tools/list but forget tools/call. For a tool to be usable:

  • It must be present in the exported array used by tools/list
  • The handler must be reachable from the call router (often a chain of if / switch / “try handler then fallback”)

A good pattern is: each module handler returns null when it does not recognize the tool name. The router tries modules in sequence until one returns a non-null result.

5) Safety checklist before you push

  • Run a syntax check: node --check src/mcp-tools.js
  • Check for duplicate exports (common when merging arrays)
  • Confirm tool names are globally unique (prefix by domain)
  • Add minimal input schema so agents get good errors early

6) Quick troubleshooting

  • Tool appears in list but call fails: dispatch chain is missing your handler
  • Node syntax error on startup: duplicate exports or malformed imports
  • Tool name collision: rename with a tighter prefix (e.g., energy.tariff.* rather than tariff.*)
