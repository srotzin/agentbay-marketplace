How to Add a New MCP Service Module in AgentBay practical wiring guide

This tutorial shows the common pattern used in src/services/, how to expose tools in a new src/mcp-tools-*.js phase file, and how to register them in src/mcp-tools.js so they appear in MCP tools/list.

1) The architecture: service module → phase tools file → MCP registry

In AgentBay, a “service module” is typically a pure JS module exporting a set of async functions that do the work. A “phase tools file” converts those functions into MCP tool definitions (name, description, JSON schema), and maps tool calls to handlers. Finally, src/mcp-tools.js aggregates all phases into one tool list and a single dispatch function. 

src/services/<your-vertical>.js
src/mcp-tools-<your-vertical>.js
src/mcp-tools.js

2) Create the service module (src/services/<vertical>.js)

Follow the existing pattern: a small set of capability-focused functions, input validation, and deterministic outputs. Keep network calls optional (or mocked) unless the repo already has the required client.

Minimal example (template)

// src/services/example-vertical.js

export async function example_healthcheck() {
  return {
    ok: true,
    service: 'example-vertical',
    checked_at: new Date().toISOString()
  };
}

export async function example_format_request({ title, notes }) {
  if (!title || typeof title !== 'string') {
    throw new Error('title must be a non-empty string');
  }

  return {
    title: title.trim(),
    notes: (notes || '').toString().trim(),
    hint: 'Pass this object into your downstream workflow.'
  };
}

Tip: Keep your exported function names aligned with your eventual MCP tool names. That makes the dispatch switch/case in the phase tools file straightforward.

3) Create a phase tools file (src/mcp-tools-<vertical>.js)

The phase file defines two exports:

  • <vertical>Tools: an array of MCP tool definitions
  • handle<Vertical>Tool: a dispatcher for tool calls

Minimal example (template)

// src/mcp-tools-example-vertical.js

import {
  example_healthcheck,
  example_format_request
} from './services/example-vertical.js';

export const exampleVerticalTools = [
  {
    name: 'example_healthcheck',
    description: 'Sanity-check the example vertical service module.',
    inputSchema: {
      type: 'object',
      properties: {},
      required: []
    }
  },
  {
    name: 'example_format_request',
    description: 'Normalize a title/notes payload for downstream workflows.',
    inputSchema: {
      type: 'object',
      properties: {
        title: { type: 'string', description: 'Short human-readable title.' },
        notes: { type: 'string', description: 'Optional extra context.' }
      },
      required: ['title']
    }
  }
];

export async function handleExampleVerticalTool(name, args) {
  switch (name) {
    case 'example_healthcheck':
      return await example_healthcheck();

    case 'example_format_request':
      return await example_format_request(args);

    default:
      throw new Error(`Unknown example-vertical tool: ${name}`);
  }
}

Tip: keep tool names globally unique and consistent (use a prefix like example_ or <domain>_).

4) Register tools in src/mcp-tools.js

Update the MCP registry file so the tool list includes your new phase and calls are routed to your handler. In most AgentBay setups, this involves:

  1. Importing <vertical>Tools and handle<Vertical>Tool
  2. Appending to the global toolsArray
  3. Extending the dispatch chain so your handler is invoked for your tool names

Checklist snippet

// 1) imports
import { exampleVerticalTools, handleExampleVerticalTool } from './mcp-tools-example-vertical.js';

// 2) tools array
const toolsArray = [
  // ... existing tools
  ...exampleVerticalTools,
];

// 3) dispatch
if (name.startsWith('example_')) {
  return await handleExampleVerticalTool(name, args);
}

5) Validate before committing

  • Run node --check src/mcp-tools.js to catch syntax errors.
  • Start the server (if your workflow includes it) and call tools/list to confirm tools appear.
  • Make sure input schemas are strict enough to avoid ambiguous arguments.

6) Common pitfalls

  • Handler not wired: tools appear in tools/list but calls fail because dispatch never reaches your handler.
  • Name collisions: two phases export the same tool name; prefix aggressively.
  • Schema drift: update inputSchema whenever you change function arguments.

7) Next steps

Once you have a basic module wired, add higher-level capabilities:

  • Batch endpoints (process multiple items in one call)
  • Deterministic validation and normalization functions
  • Small “planner” helpers that output structured action plans (not just text)

This page is intentionally self-contained and written to match the AgentBay repo layout. If the project structure changes, update the file paths and import examples accordingly.
