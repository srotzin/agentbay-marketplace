How to automate insurance claims with AI agents

A practical, end-to-end tutorial for building a claims assistant that can intake FNOL, classify severity, request missing documents, update stakeholders, and hand off to adjusters when needed.

1) Architecture: agent + tools + audit trail

What you build

  • Claims Intake Agent: chats with the claimant, gathers structured facts, and creates a claim record.
  • Claims Ops Tools: deterministic actions (create claim, request documents, schedule inspection, update status).
  • Audit Log: a durable record of tool calls, evidence, and rationale for compliance + dispute resolution.

Why this works

  • Agents are best at messy language, ambiguity, and prioritization.
  • Tools are best at consistent execution and integrations.
  • Separation makes outcomes explainable: every action is a tool call tied to evidence.
Key constraint: the agent should never “decide” coverage. It can summarize facts, detect missing information, and propose next steps — but coverage decisions and settlement amounts must be done by policy rules + adjuster review.

2) Claim workflow as a state machine

Model the claim as explicit states. This prevents the agent from skipping steps, and makes back-office handoffs clean.

NEW (FNOL) → TRIAGE → DOCS_PENDING → INVESTIGATION → REVIEW → APPROVED|DENIED → SETTLEMENT → CLOSED

Suggested state transitions

  • NEW → create claim, confirm contact info, incident basics, and coverage type.
  • TRIAGE → classify severity (low/med/high) and fraud risk (low/med/high) with conservative thresholds.
  • DOCS_PENDING → request missing documents and set reminders.
  • INVESTIGATION → schedule inspection / repair estimate / police report follow-up.
  • REVIEW → package a summary for an adjuster with evidence links.
  • SETTLEMENT → status updates, payment method confirmation, final notice.

3) Tool interface design (MCP style)

Keep tools small, typed, and safe. Your agent calls tools; tools enforce permissions, validation, and logging.

Minimal tool set

  • claims.create (structured FNOL)
  • claims.update (status, notes)
  • claims.request_documents (checklist + channels)
  • claims.schedule_inspection (time windows)
  • claims.generate_adjuster_packet (facts + evidence)
  • messaging.send (templated updates)

Example tool schema

{
  name: "claims.create",
  description: "Create a new claim from FNOL data",
  inputSchema: {
    type: "object",
    properties: {
      policyNumber: { type: "string" },
      claimant: {
        type: "object",
        properties: {
          fullName: { type: "string" },
          phone: { type: "string" },
          email: { type: "string" }
        },
        required: ["fullName"]
      },
      incident: {
        type: "object",
        properties: {
          lossType: { type: "string", enum: ["auto", "property", "liability", "health"] },
          occurredAt: { type: "string", description: "ISO timestamp" },
          location: { type: "string" },
          narrative: { type: "string" }
        },
        required: ["lossType", "narrative"]
      }
    },
    required: ["claimant", "incident"]
  }
}

Guardrails you want in every tool

  • Idempotency keys for create operations.
  • Explicit permission checks (claimant vs. adjuster vs. supervisor).
  • Templated messaging rather than freeform, to reduce compliance risk.
  • Redaction of sensitive fields from logs by default.

4) Agent prompts: policies, safety, and compliance

System rules (examples)

  • Never promise coverage, payout, or timelines.
  • When uncertain: ask for clarification, or escalate to adjuster.
  • Prefer tool calls for any record change; never fabricate claim IDs.
  • Use least-privilege tools; do not access claims unrelated to the current claimant.

Conversation skeleton

1) Confirm identity + policy
2) Collect incident facts (when/where/what)
3) Collect impact (damage, injuries, vehicles, parties)
4) Request evidence (photos, reports, receipts)
5) Summarize + confirm accuracy
6) Create claim (tool call)
7) Next steps + expected updates

5) Evaluation: accuracy, leakage, latency

Offline evaluation set

  • 50–200 synthetic FNOL conversations (varied loss types).
  • Golden structured output: fields + required document checklist.
  • Adversarial cases: contradictory narratives, missing dates, prompt injection attempts.

Metrics that matter

  • Field accuracy: did you extract the right facts?
  • Escalation rate: are humans pulled in appropriately?
  • Cycle time: time to reach “adjuster packet ready”.
  • Customer satisfaction: post-interaction CSAT.

6) Deployment checklist

  • Log every tool call with timestamp, actor, and claim ID.
  • Store evidence links (photos, PDFs) and track whether they were verified.
  • Implement rate limits + abuse handling on inbound channels.
  • Provide an adjuster UI for quick review + override.
  • Run a staged rollout: internal → friendly customers → broad release.
