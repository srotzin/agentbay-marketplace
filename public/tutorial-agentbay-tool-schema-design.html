MCP Tool Schema Design: Reliable Inputs + Outputs

If a tool schema is too loose, agents invent parameters. If it is too strict, it becomes hard to use. This guide focuses on the practical middle ground: schemas that are easy for agents to call correctly and easy for service modules to implement safely.

Why schema design matters

MCP tools are called by language models. That means your schema is both an API contract and part of the prompt. The best schemas minimize ambiguity by doing three things:

  1. Constrain inputs so the model can’t easily guess wrong.
  2. Describe intent so the model knows what you want, not just the field names.
  3. Guarantee predictable outputs so downstream steps don’t break.

Input schema checklist (agent-friendly)

  • Use explicit names. Prefer facilityId over id, customerEmail over email.
  • Make critical fields required. If a call cannot succeed without it, put it in required.
  • Add descriptions with constraints. Include formats, allowed units, max lengths, and examples.
  • Keep unions rare. If a field can be “string or object”, agents often pick the wrong branch.
  • Prefer enums for small sets. Use enum for fields like priority, sortOrder, region.
  • Use structured filters. For search tools, prefer filters: { status: 'open', createdAfter: '...' } over a single free-text string.

Designing outputs: stable and composable

Even if your tool returns “text”, you can still return structured JSON. A few patterns improve reliability:

  • Always include a top-level ok boolean and a short summary string.
  • Separate metadata from results: { ok, summary, result: {...}, meta: {...} }.
  • Use arrays for lists and include a total count if known.
  • Include a warnings array for partial success (missing fields, truncated results).
// Example tool result
{
  "ok": true,
  "summary": "Found 12 work orders",
  "result": {
    "workOrders": [
      { "id": "WO-1001", "status": "open", "site": "Plant A" }
    ],
    "nextCursor": "..."
  },
  "meta": { "generatedAt": "2026-04-13T00:00:00Z" },
  "warnings": []
}

Idempotency and safety (the overlooked part)

When agents interact with tools, they may retry calls. Design inputs so a retry does not create duplicates:

  • Add idempotencyKey to tools that create resources.
  • Use dryRun for actions that could have side effects.
  • Return deterministic errors: include errorCode and retryable.
// Example error payload
{
  "ok": false,
  "summary": "Missing required field: facilityId",
  "error": {
    "errorCode": "VALIDATION_ERROR",
    "retryable": false,
    "details": { "missing": ["facilityId"] }
  }
}

Pagination pattern for list/search tools

If a tool can return many results, add pagination on day one:

  • limit: a reasonable max (e.g. 50 or 100).
  • cursor: opaque token returned from the previous call.
  • sort: explicit sort field + direction if applicable.
// Example list tool input
{
  "filters": { "status": "open" },
  "limit": 50,
  "cursor": null
}

Common failure modes (and fixes)

  • Ambiguous date fields. Use ISO timestamps and state timezone expectations in the description.
  • Free-text “query” for everything. Split into structured filters plus an optional free-text query.
  • Tools that return unstructured logs. Return JSON with a logs array if you need debugging.
  • Too many optional fields. Agents omit them; then your service guesses. Make the core required.

Quick template you can copy

export const tools = [
  {
    name: 'my_prefix_action',
    description: 'One sentence: what this does and what it returns.',
    inputSchema: {
      type: 'object',
      properties: {
        // required core
        targetId: { type: 'string', description: '...' },
        // optional modifiers
        dryRun: { type: 'boolean', description: 'If true, do not persist changes.' },
        idempotencyKey: { type: 'string', description: '...' }
      },
      required: ['targetId']
    }
  }
];

export async function handleTool(name, args, ctx) {
  switch (name) {
    case 'my_prefix_action':
      return await doAction(args, ctx);
    default:
      return null;
  }
}
