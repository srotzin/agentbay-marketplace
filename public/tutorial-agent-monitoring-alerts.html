Monitoring & Alerts for AI Agents: A Practical Tutorial

Agents fail differently than traditional services: tool calls time out, prompts drift, and upstream APIs change. This guide shows a simple, production-friendly way to add logs, metrics, traces, and alerting.

Who this is for: builders shipping agents that call tools, handle long-running workflows, or coordinate multiple workers.
Estimated time: 15–25 minutes.

1) Start with the observability triangle

Logs
  • Answer: “What happened?”
  • Best for: debugging, audits, replaying runs
  • Agent-specific: prompt + tool-call transcript (redacted)
Metrics
  • Answer: “How often, how bad?”
  • Best for: SLOs, alerting, capacity planning
  • Agent-specific: tool error rate, retries, tokens, latency
Traces
  • Answer: “Where is time spent?”
  • Best for: identifying slow tools or stuck steps
  • Agent-specific: span per tool call + reasoning step
Alerts
  • Answer: “Who needs to act now?”
  • Best for: incidents and regressions
  • Agent-specific: hallucinated tool args, output validation failures

2) Define the minimal event schema

Your agent should emit structured events so you can aggregate across runs. Keep it stable and versioned. 

{
  "event_version": 1,
  "timestamp": "2026-04-11T08:15:00Z",
  "env": "prod",
  "agent": {
    "name": "support-triage",
    "release": "2026.04.11",
    "run_id": "run_9d1c..."
  },
  "step": {
    "name": "call_tool",
    "tool": "search_email",
    "attempt": 1
  },
  "timing_ms": 842,
  "result": "ok",
  "redactions": ["email_body"],
  "metadata": {
    "customer_tier": "enterprise"
  }
}
Tip: Always include run_id and tool (when applicable). Those two fields unlock most dashboards.

3) Instrument tool calls with spans

A single agent run is usually a tree: an overall “run” span, then one span per step, and a child span per tool call. 

// Pseudocode
span("agent.run", { run_id, agent })
  .withChild(span("step.plan"))
  .withChild(span("tool.call", { tool: "search_web" }, async () => {
    const t0 = now();
    try {
      const res = await callTool(...);
      metric.count("tool_success", 1, { tool: "search_web" });
      metric.hist("tool_latency_ms", now() - t0, { tool: "search_web" });
      return res;
    } catch (err) {
      metric.count("tool_error", 1, { tool: "search_web", code: err.code || "unknown" });
      log.error({ err, tool: "search_web", run_id });
      throw err;
    }
  }))

4) Add agent-specific metrics

  • Success rate: completed runs / started runs
  • Tool error rate: tool failures per tool and per upstream provider
  • Retries: retry count distribution per tool
  • Latency: p50/p95 per tool and per end-to-end run
  • Cost signals: tokens in/out, calls per run
  • Validation failures: schema parse errors, policy violations, bad outputs

5) Create alerts that don’t page you for noise

Alerting for agents works best when you alert on user impact, not internal errors. For example, alert when “failed runs exceed 2% for 10 minutes”, not on every tool timeout.

Recommended alerts
  • Run failure rate > threshold
  • Tool error rate spike for a single provider
  • p95 run latency regression
  • Output validation failures spike
Avoid as primary pages
  • Single tool timeout (often transient)
  • Single malformed input
  • One-off token spikes

6) Operational playbooks: the 3 questions

  1. Is this widespread? Check run failure rate and compare across releases.
  2. Is it a tool provider? Slice errors by tool + upstream API.
  3. Is it prompt/release drift? Compare validation failures between versions.

7) Add replay for safe debugging

Store enough context to reproduce problems without exposing sensitive data: versioned prompts, tool inputs/outputs (redacted), and deterministic seeds if supported.

Simple replay checklist
  • Log prompt template ID + variables (not raw secrets)
  • Persist tool call arguments and results (redacted + encrypted)
  • Record model + temperature + response format constraints
  • Record agent release/version

8) Next steps

  • Start by instrumenting only tool calls + run-level outcome.
  • Add validation metrics next (they catch regressions early).
  • Promote the best dashboards to a shared “agent health” landing page.
