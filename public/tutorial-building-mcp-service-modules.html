How to Build a New MCP Service Module

A practical guide for AgentBay contributors: add a new vertical module, wire it into a phase file, and validate it locally.

Home / Tutorial / Building MCP service modules

What you are building

In AgentBay, a service module is a small generator that returns one or more MCP tools for a specific vertical. Service modules live in src/services/ and are composed into phase files that feed public/openapi.json.

Goal: Add a new vertical with a clean, repeatable pattern ("hitl.js style").
Tip: Start with one tool, validate the schema end-to-end, then scale up.

Step 0: Pick a vertical and define the tool surface

Before writing code, decide:

  • Service name (short, kebab-case): e.g. fraud-monitoring
  • What inputs are required (be strict): strings, enums, arrays
  • What the tool returns: usually a JSON object with predictable fields

If you are unsure, review existing modules under src/services/ and mirror their style.

Step 1: Create the service module file

Create a new file under src/services/, exporting a single function. The function should return an array of tool definitions. 

// src/services/fraud-monitoring.js

export function fraudMonitoring() {
  return [
    {
      name: "fraud_monitoring_alert_triage",
      description: "Triage a fraud alert and return recommended next actions.",
      inputSchema: {
        type: "object",
        additionalProperties: false,
        required: ["alert"],
        properties: {
          alert: {
            type: "object",
            description: "The raw alert payload from your provider."
          },
          riskTolerance: {
            type: "string",
            enum: ["low", "medium", "high"],
            default: "medium"
          }
        }
      }
    }
  ];
}
Pattern notes
  • Prefer additionalProperties: false to keep schemas crisp.
  • Use small, composable tools instead of one giant tool.

Step 2: Wire the module into a phase file

Phase files live under src/mcp-tools/ and compose tools from services. If you are adding a new batch, create a new phase file and import your module. 

// src/mcp-tools/mcp-tools-phaseXX.js

import { fraudMonitoring } from "../services/fraud-monitoring.js";

export const phaseXXTools = [
  ...fraudMonitoring(),
];

Step 3: Register the phase in mcp-tools.js

src/mcp-tools.js collects tool arrays from every phase file. Add your new phase export and append its tools. 

// src/mcp-tools.js

import { phaseXXTools } from "./mcp-tools/mcp-tools-phaseXX.js";

export const mcpTools = [
  // ...existing phases...
  ...phaseXXTools,
];

Step 4: Validate locally (fast checks)

Run quick syntax checks on the new files, then run the project build/generation step you normally use. 

# Syntax check
node --check src/services/fraud-monitoring.js
node --check src/mcp-tools/mcp-tools-phaseXX.js

# Optional: run whatever script updates public/openapi.json
# npm test / npm run build / node scripts/generate-openapi.js
Done when: the app boots, your new tool appears in the OpenAPI output, and there are no schema validation errors.

Troubleshooting

My tool does not show up

  • Confirm your service function is actually included in a phase file.
  • Confirm the phase export is appended in src/mcp-tools.js.
  • Search for duplicate tool names and rename to be globally unique.

Schema or runtime errors

  • Make sure required matches your properties.
  • Set additionalProperties: false to catch typos early.
  • Use strings/enums for stable interfaces; keep objects for nested payloads.
