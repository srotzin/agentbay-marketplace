MCP Phase Modules: How HiveAgent Structures Tools (and How to Add Your Own)

HiveAgent’s MCP server exposes a growing set of tools. To keep the codebase maintainable, tools are grouped into phase modules (small files that each export a bundle of related tools). This guide explains the pattern and provides a checklist for adding a new vertical.

Who this is for: developers adding new vertical tools (e.g., “Forestry Operations”, “Water Treatment Operations”, etc.).
Goal: add tools without breaking the dispatch chain or tool list.

What is a “phase module”?

A phase module is a file in src/ (commonly named like mcp-tools-phaseXX-*.js) that exports:

  • tools: an array of MCP tool definitions
  • handlers (or similarly named export): a mapping from tool name to implementation

The server’s central registry (src/mcp-tools.js) imports each phase module, concatenates their tools into a single list, and routes tool invocations to the correct handler.

Why bundle tools this way?

Faster iteration

New verticals ship as small, reviewable diffs instead of one large file.

Lower risk

When tools are grouped, you can reason about dependencies and naming collisions more easily.

Clear ownership

Each module can represent a domain area (operations, compliance, estimation, checklists, etc.).

Predictable wiring

The central registry only needs an import + tool merge + dispatch hook.

Naming conventions that prevent collisions

  • Use a tool prefix that encodes the vertical, e.g. forestry_*, water_treatment_*, museum_*, etc.
  • Keep tool names stable once published: clients may store tool names in prompts, workflows, or saved templates.
  • Prefer verbs that match outcomes: estimate, plan, checklist, summarize, convert.

Step-by-step: add a new vertical module safely

  1. Create a new phase module file under src/.
    Tip: keep each phase module focused (2–6 tools is usually plenty).
  2. Export your tool definitions with clear descriptions and explicit input schemas.
  3. Export a handler map and ensure each tool name has a matching handler implementation.
  4. Wire into src/mcp-tools.js:
    • Import your new module
    • Add tools to the exported tools list
    • Extend the handler dispatch chain
  5. Run a syntax check: 
    node --check src/mcp-tools.js
  6. Test a sample invocation (locally or via whatever harness the repo uses).

A minimal module skeleton

// src/mcp-tools-phaseXX-your-vertical.js

export const tools = [
  {
    name: "your_vertical_do_thing",
    description: "Explain what it does in one sentence.",
    inputSchema: {
      type: "object",
      properties: {
        example: { type: "string", description: "An example input" }
      },
      required: ["example"]
    }
  }
];

export const handlers = {
  async your_vertical_do_thing(args) {
    // Validate, compute, return structured output
    return { ok: true };
  }
};

Common mistakes (and quick fixes)

  • Tool appears in list but fails when called: handler name mismatch or missing dispatch wiring.
  • Runtime crash after adding module: syntax error, circular import, or missing export.
  • Tool name collision: rename with a stronger prefix; avoid generic names like calculate.
  • Inconsistent output shapes: return a consistent JSON object; avoid mixing plain strings and objects across tools.

Where to go next

If you’re new to MCP concepts, start by reading your server’s /docs/ pages in this site. Then look at existing phase modules in src/ to copy the established style.
